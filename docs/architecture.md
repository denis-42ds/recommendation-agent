# Architecture — Recommendation Agent MVP

**Дата:** 25.11.2026  
**Статус:** DECISION — архитектура MVP.

## 1. Архитектурный принцип

Для MVP используется простой модульный монолит: одно приложение, один процесс Python, один контейнер при деплое.

Цель — минимизировать время разработки и количество точек отказа.

## 2. Технологический стек

| Компонент | Технология | Статус |
|---|---|---|
| Язык | Python 3.11+ | DECISION |
| UI | Streamlit | DECISION |
| Recommendation Engine | Python | DECISION |
| Данные | JSON | DECISION |
| Тесты | pytest | DECISION |
| Контейнеризация | Docker | DECISION |
| Публичный хостинг | Google Cloud Run | DECISION |

FastAPI на первом этапе не требуется. Его можно добавить, если появится отдельный API-сценарий.

## 5. Модули

### app.py

Отвечает за:
- интерфейс Streamlit;
- выбор клиента;
- отображение информации о клиенте;
- запуск recommendation engine;
- отображение рекомендаций и объяснений.

### recommender.py

Отвечает за:
- получение контекста;
- генерацию кандидатов;
- применение бизнес-фильтров;
- расчёт score;
- формирование результата.

### data/

Содержит демонстрационные данные:
- клиентов;
- товаров и услуг;
- покупок и, при необходимости, лицензий.

## 6. Алгоритм рекомендаций

### Шаг 1. Candidate Generation

Формирование кандидатов из каталога на основе:
- истории покупок;
- связанных товаров;
- активных лицензий;
- выбранного сценария рекомендации.

### Шаг 2. Business Filtering

Исключение предложений, которые:
- отсутствуют в каталоге;
- не соответствуют бизнес-правилам;
- не подходят выбранному сценарию;
- не должны повторно предлагаться клиенту.

### Шаг 3. Ranking

Расчёт оценки кандидата на основе доступных признаков и правил.

**ASSUMPTION:** начальная версия использует простую взвешенную систему scoring. Веса задаются явно и могут корректироваться после тестирования.

### Шаг 4. Explanation

Формирование объяснения на основании:
- фактов о клиенте;
- характеристик товара;
- применённых правил;
- reason_codes.

В первой версии объяснения формируются обычным Python-кодом.

## 7. Роль LLM

LLM не участвует в определении бизнес-фактов.

Если LLM будет подключена, ей можно поручить переформулирование уже рассчитанного объяснения для пользователя.

Запрещено поручать модели:
- придумывать товары и SKU;
- определять цены;
- придумывать наличие;
- самостоятельно определять совместимость;
- обходить бизнес-фильтры;
- менять результаты ранжирования без проверяемого основания.

При недоступности LLM приложение продолжает работу.

## 8. Развёртывание

### Локально

```text
Browser
   |
   v
Streamlit
   |
   v
Python Recommendation Engine
   |
   v
JSON data
```

### Cloud Run

Один Docker-контейнер с Streamlit-приложением.

Предварительные параметры:
- регион: `asia-southeast3`;
- CPU: 1;
- RAM: 1 GiB;
- minimum instances: 0;
- maximum instances: 1.

Параметры уточняются после проверки приложения.

### Резервный вариант

ngrok для временного публичного HTTPS-доступа, если деплой в Cloud Run не удастся выполнить вовремя.

## 9. Принципы безопасности

- Не хранить секреты в исходном коде.
- Не коммитить `.env`.
- Не использовать реальные персональные данные без разрешения.
- Для демонстрации применять синтетические данные.
- Не доверять LLM при проверке бизнес-ограничений.

## 10. Критерии пересмотра архитектуры

Изменять архитектуру только если:
- текущий подход не позволяет выполнить требования;
- появляется подтверждённая необходимость в отдельном API;
- объём данных перестаёт помещаться в простое файловое хранилище;
- возникает конкретная проблема производительности или надёжности.

Не добавлять инфраструктуру ради потенциального будущего масштабирования.
