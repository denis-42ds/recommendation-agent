# Requirements — Recommendation Agent MVP

**Дата актуализации:** 27.11.2026
**Статус:** scope сокращён для завершения демонстрируемого MVP в оставшееся время.

## 1. Назначение

Recommendation Agent формирует персонализированные рекомендации для клиента интернет-магазина Softline на основе истории покупок, доступного каталога и проверяемых бизнес-правил.

Целевой продукт предусматривает:
- Cross-sell — дополняющие товары и услуги.
- Up-sell — расширенные или более подходящие решения.
- Renewal — продление лицензий и подписок.

**Приоритет реализации в хакатонном MVP: Cross-sell.** Остальные сценарии не должны задерживать завершение рабочего Cross-sell.

## 2. Границы и сегменты

- B2B и B2C обрабатываются раздельно.
- Для B2C запрещено использовать отрасль (`industry`) и корпоративный профиль клиента.
- Для B2B допустимы только фактически доступные и разрешённые поля.
- Не выводить отсутствующие сведения о лицензиях, совместимости, ценах или наличии.

## 3. MUST — функциональность демонстрации

| ID | Требование |
|---|---|
| FR-01 | Пользователь может выбрать демонстрационного клиента |
| FR-02 | Система загружает доступную историю и сегмент клиента |
| FR-03 | Система генерирует кандидатов для Cross-sell |
| FR-04 | Система исключает уже приобретённые товары |
| FR-05 | Система исключает товары, отсутствующие в используемом каталоге |
| FR-06 | Система ранжирует кандидатов и возвращает Top-3 |
| FR-07 | Для каждой рекомендации отображаются `product_id`, тип, `score`, `reason_codes`, `evidence`, `explanation` |
| FR-08 | Объяснение формируется только из фактов и применённых правил |
| FR-09 | Основная функциональность работает без LLM |
| FR-10 | Результат доступен через Streamlit UI |
| FR-11 | Система корректно обрабатывает cold-start и недостаток кандидатов |
| FR-12 | B2B и B2C логика разделена; B2C не использует отрасль или корпоративный профиль |

## 4. Контракт рекомендации

Минимальная структура:

```json
{
  "product_id": "catalog_product_id",
  "recommendation_type": "cross_sell",
  "score": 0.0,
  "reason_codes": ["CO_PURCHASE"],
  "evidence": {
    "source_item_ids": ["purchased_item_id"],
    "co_purchase_count": 0
  },
  "explanation": "Товар часто встречался в корзинах вместе с ранее приобретённым товаром."
}
```

Пример иллюстративный, не является фактической рекомендацией или данными каталога.

Требования:
- `product_id` должен ссылаться на существующую запись каталога.
- `score` должен быть детерминированным и воспроизводимым.
- `reason_codes` должны соответствовать реально сработавшим правилам.
- `evidence` должен содержать идентификаторы и измеримые факты, достаточные для проверки объяснения.
- Не придумывать SKU, цену, наличие, сроки лицензии или совместимость.

## 5. Минимальная логика Cross-sell

Приоритетные источники кандидатов:
1. Co-purchase: товары, встречавшиеся в одной Train-корзине с товарами из истории клиента.
2. Popularity fallback: популярные товары подходящего сегмента/каталога, если co-purchase кандидатов недостаточно.

Фильтры:
- исключить товары, уже купленные клиентом;
- исключить товары вне допустимого каталога;
- исключить невалидные или неоднозначно сопоставленные записи;
- применять сегментные ограничения только если они подтверждены данными и правилами.

Ранжирование:
- использовать простую детерминированную формулу;
- при равенстве score использовать стабильный tie-break;
- не усложнять модель в оставшееся время.

Cold-start:
- если истории покупок нет, использовать допустимый popularity fallback;
- явно помечать рекомендацию как неперсонализированную;
- если допустимых товаров недостаточно, не заполнять список выдуманными позициями.

## 6. Explainability

Разрешённые основания:
- кандидат встречался вместе с конкретным ранее купленным товаром;
- кандидат входит в popularity fallback на основании Train;
- кандидат прошёл конкретные бизнес-фильтры.

Запрещено:
- утверждать техническую совместимость на основании одной совместной покупки;
- утверждать, что товар подходит по отрасли в B2C;
- генерировать объяснения, не подтверждённые `evidence`.

## 7. Качество и проверка

Обязательные проверки:
- отсутствие уже купленных товаров в результате;
- все рекомендации существуют в каталоге;
- B2C не использует запрещённые признаки;
- детерминированность ранжирования;
- корректный Top-3 и поведение при недостатке кандидатов;
- объяснение соответствует `reason_codes` и `evidence`;
- cold-start fallback работает без ошибки.

Offline-метрики:
- Precision@K, Recall@K, NDCG@K, MAP@K;
- Coverage, Diversity, Fill Rate, Latency.

Backtest-протокол уже зафиксирован в `docs/STATE.md`; не менять его ради улучшения цифр.

## 8. Не входит в текущий scope

- Полноценный Up-sell и Renewal.
- LLM в критическом пути.
- RAG, vector DB, отдельная БД.
- FastAPI и микросервисы.
- Обучение ML-модели.
- Автоматическое обогащение каталога внешними источниками.
- Дальнейшая оптимизация Match Rate каталога, если это не блокирует корректную рекомендацию.

## 9. Нефункциональные требования

- Локальный запуск на Python 3.11+.
- Минимум зависимостей.
- Повторяемый результат.
- Никаких секретов в репозитории.
- Реальный датасет не публиковать; для публичного демо использовать синтетические/обезличенные данные.
- Не заявлять рост конверсии или выручки без подтверждённого эксперимента.
