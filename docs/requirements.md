# Requirements — Recommendation Agent MVP

**Дата:** 25.11.2026  
**Статус:** базовые требования зафиксированы; часть бизнес-деталей требует уточнения.

## 1. Назначение продукта

Recommendation Agent формирует персонализированные рекомендации для клиента B2B интернет-магазина на основе доступного контекста, истории покупок, профиля клиента, активных лицензий, каталога и бизнес-правил.

Цель MVP — продемонстрировать полный путь от выбора клиента до выдачи обоснованных рекомендаций.

## 2. Основные сценарии

### Cross-sell

Предложение дополняющих товаров и услуг к уже приобретённым или используемым решениям.

### Up-sell

Предложение более подходящих, расширенных или функциональных решений.

### Renewal

Предложение продления лицензий и подписок.

## 3. Контекст рекомендаций

В целевой системе могут использоваться:

- история покупок;
- профиль и сегмент клиента;
- активные лицензии;
- контекст текущего визита;
- каталог товаров и услуг;
- бизнес-правила.

**ASSUMPTION для MVP:** если реальные данные недоступны, используются синтетические демонстрационные данные. Они должны быть явно обозначены как синтетические.

## 4. Функциональные требования MVP

| ID | Требование | Приоритет |
|---|---|---|
| FR-01 | Пользователь может выбрать клиента для демонстрации | MUST |
| FR-02 | Система загружает контекст выбранного клиента | MUST |
| FR-03 | Система формирует кандидатов на рекомендации | MUST |
| FR-04 | Система исключает недопустимые предложения по бизнес-правилам | MUST |
| FR-05 | Система ранжирует оставшиеся рекомендации | MUST |
| FR-06 | Для рекомендации отображается тип: cross-sell, up-sell или renewal | MUST |
| FR-07 | Для рекомендации отображается объяснение | MUST |
| FR-08 | Пользователь видит исходные факты, на которых основана рекомендация | SHOULD |
| FR-09 | При отсутствии LLM система продолжает работать | MUST |
| FR-10 | Результат доступен через простой веб-интерфейс | MUST |

## 5. Требования к результату рекомендации

По возможности каждая рекомендация должна содержать:

- `product_id`;
- `recommendation_type`;
- `score`;
- `reason_codes`;
- `evidence`;
- `explanation`.

Товар должен существовать в каталоге. Нельзя генерировать несуществующие SKU, цены, наличие или совместимость.

## 6. Требования к объяснимости

Объяснение должно опираться на факты из данных и результаты бизнес-логики.

Примеры допустимых оснований:
- клиент ранее приобрёл связанный товар;
- у клиента есть лицензия с приближающейся датой окончания;
- товар относится к нужному сегменту;
- товар соответствует заданному правилу совместимости.

**ASSUMPTION:** для демонстрации достаточно краткого текстового объяснения и списка кодов причин.

## 7. Нефункциональные требования

- Локальный запуск на компьютере разработчика.
- Публичный HTTPS-доступ к демо.
- Минимальное количество внешних сервисов.
- Предсказуемая работа без LLM.
- Отсутствие секретов в исходном коде.
- Возможность проверить базовую логику автоматическими тестами.

## 8. Ограничения MVP

Не включать без необходимости:
- микросервисную архитектуру;
- multi-agent;
- RAG и vector database;
- обучение собственной ML-модели;
- сложную авторизацию;
- отдельную базу данных, если JSON достаточно;
- отдельный FastAPI backend, если Streamlit закрывает сценарий демонстрации;
- CI/CD.

## 9. Оценка качества

При наличии достаточных тестовых данных можно рассчитать:
- Precision@K;
- Recall@K;
- NDCG@K;
- Coverage;
- Diversity.

Для демонстрации также фиксировать:
- время формирования рекомендаций;
- ошибки;
- доступность приложения;
- стоимость модельных вызовов, если LLM будет подключена.

Не заявлять рост конверсии или выручки без подтверждающего эксперимента.
