# Материалы для подачи — Recommendation Agent

**Проект:** Recommendation Agent для личного кабинета интернет-магазина Softline  
**Хакатон:** «ИИкузница 2026»  
**Дата актуализации:** 27.11.2026

## 1. Выполнение задачи за 48 часов

**Статус: выполнено.**

В рамках MVP реализован Cross-sell-сценарий рекомендательной системы:

- обработка истории покупок клиента;
- раздельная обработка сегментов B2B и B2C;
- генерация кандидатов на основе графа совместных покупок;
- popularity fallback, если персональных кандидатов недостаточно;
- исключение уже приобретённых товарных групп;
- фильтрация по доступным предложениям каталога;
- детерминированная выдача Top-3;
- объяснение рекомендаций на основе фактических данных;
- обработка cold-start — клиентов без истории покупок.

Up-sell и Renewal не реализовывались: они не входят в scope текущего MVP.

## 2. Подход и архитектура

Использован подход модульного монолита. Интерфейс, загрузчик данных и движок рекомендаций работают в рамках одного Python-приложения.

Основной конвейер:

1. **Customer Context** — получение сегмента клиента и истории покупок.
2. **Candidate Generation** — генерация кандидатов по графу совместных покупок.
3. **Business Filtering** — исключение уже приобретённых товарных групп и недоступных предложений.
4. **Ranking / Scoring** — детерминированное ранжирование кандидатов.
5. **Explanation** — формирование объяснений из реальных evidence и reason codes.
6. **Top-3** — возврат до трёх допустимых рекомендаций.

Если co-purchase-кандидатов недостаточно, свободные позиции заполняются популярными товарами соответствующего сегмента.

Для клиентов без истории используется popularity соответствующего сегмента. Такие рекомендации маркируются как неперсонализированные.

B2B и B2C обрабатываются раздельно. Для B2C не используются отрасль (`industry`) и корпоративный профиль клиента.

Граф отражает совместные покупки в корзинах и не является доказательством технической совместимости товаров.

## 3. Стек и модели

**Используемые технологии:**

- Python 3.11+;
- Streamlit — пользовательский интерфейс;
- pandas — обработка табличных данных;
- openpyxl — чтение Excel;
- matplotlib — визуализация;
- pytest — автоматические тесты;
- Ruff — статический анализ и проверка стиля;
- Docker — контейнеризация;
- Google Cloud Run — размещение приложения;
- Google Artifact Registry — хранение Docker-образа.

**Модели машинного обучения и LLM:**

В текущем MVP внешние LLM API и обученные ML-модели не используются. Рекомендации строятся детерминированным алгоритмом на основе статистики совместных покупок и популярности товаров.

LLM не участвует в выборе товаров, ранжировании, определении SKU, цены или наличия. Объяснения формируются из фактических данных алгоритма.

## 4. Экономика решения

В текущей версии стоимость вызова моделей составляет **0 ₽ на один запрос**, поскольку LLM/ML API не вызываются.

Расчёт в шаблоне организаторов:

- строки вызовов моделей не заполняются;
- итоговая стоимость моделей на запрос — `0.0000 ₽`;
- в комментарии указывается, что инфраструктурные расходы не входят в расчёт стоимости моделей.

Инфраструктурные расходы Google Cloud Run и Artifact Registry являются отдельной статьёй затрат. Они зависят от фактического потребления ресурсов, количества запросов, времени работы и объёма хранения образов.

Нулевую стоимость моделей нельзя трактовать как нулевую стоимость эксплуатации всего решения.

## 5. Запуск и передача решения

### Локальный запуск

Требуются Python 3.11+ и подготовленные данные/артефакты проекта.

```bash
python -m pip install -e ".[dev]"
streamlit run app.py
```

### Запуск в Docker

Сборка:

```bash
docker build -t recommendation-agent:local .
```

Запуск:

```bash
docker run --rm -p 8080:8080 recommendation-agent:local
```

После запуска приложение доступно по адресу:

```text
http://localhost:8080
```

## 6. Ранее созданные компоненты и лицензии

Проект использует стандартные компоненты Python-экосистемы: Streamlit, pandas, openpyxl, matplotlib, pytest и Ruff.

Точные версии установленных локально пакетов зафиксированы в окружении разработчика. При этом зависимости в `pyproject.toml` заданы нижними границами версий, а не полным lock-файлом. Поэтому версии пакетов внутри Docker-образа могут отличаться от локального окружения.

Полный перечень лицензий прямых и транзитивных зависимостей необходимо подтверждать по метаданным фактически используемого окружения. Нельзя считать список основных библиотек полным аудитом всех зависимостей.

Для фиксации лицензий рекомендуется сформировать отчёт командой:

```bash
python -m pip install pip-licenses
pip-licenses --format=markdown > docs/THIRD_PARTY_LICENSES.md
```

Используемые инфраструктурные сервисы Google Cloud предоставляются на условиях соответствующих соглашений Google Cloud.

## 7. Ограничения и дальнейшее развитие

- Реализован Cross-sell; Up-sell и Renewal не входят в текущий MVP.
- Интеграция с реальным личным кабинетом Softline не подтверждена.
- Обратная связь по кликам и показам рекомендаций не реализована.
- Онлайн-эксперимент и оценка влияния на конверсию/выручку не проводились.
- Исторические снимки каталога и наличия отсутствуют.
- Сопоставление с каталогом неполное: в последнем подтверждённом запуске сопоставлено 438 из 817 `item_id`.
- Есть расхождения локальных результатов Co-purchase backtest с официальными результатами организаторов; причина требует отдельного анализа.

Fill Rate 100% в диагностическом прогоне характеризует заполненность трёх рекомендательных позиций, но не доказывает релевантность рекомендаций или рост бизнес-метрик.
