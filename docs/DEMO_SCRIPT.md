# DEMO SCRIPT — Recommendation Agent

**Дата:** 27.11.2026
**Назначение:** трёхминутная запись MVP для хакатона «ИИкузница 2026».

## 1. Что демонстрируем

Публично доступный Recommendation Agent для личного кабинета интернет-магазина Softline:

- выбор B2B/B2C;
- персональные Cross-sell рекомендации по истории покупок;
- evidence и объяснение каждой рекомендации;
- popularity fallback;
- cold-start для клиента без истории;
- работу приложения в публичном Cloud Run deployment.

**Публичный URL:**

https://recommendation-agent-ug7evithwa-eu.a.run.app

## 2. Подготовка перед записью

1. Открыть публичный URL и убедиться, что приложение загружается.
2. Проверить интерфейс на компьютере.
3. Повторить smoke test на мобильном устройстве после изменения Cloud Run concurrency на 80.
4. Заранее определить клиента B2B с историей покупок.
5. Заранее определить клиента B2C с историей покупок.
6. Заранее определить клиента без истории.
7. Убедиться, что выбранные клиенты действительно показывают нужные состояния интерфейса.
8. Подготовить вкладку с краткой архитектурой или итоговыми диагностическими показателями, если они будут показаны в записи.

Перед записью не менять алгоритм и не пересобирать Docker-образ без необходимости.

## 3. Сценарий записи — около 3 минут

### 0:00–0:20 — Введение

Показать публичное приложение.

Текст:

> Это MVP рекомендательного агента для личного кабинета интернет-магазина Softline. В рамках хакатона мы сфокусировались на Cross-sell: система предлагает товары на основе истории совместных покупок и дополняет выдачу популярными товарами соответствующего сегмента, если персональных кандидатов недостаточно.

### 0:20–1:05 — Клиент с историей, B2B

1. Выбрать B2B.
2. Выбрать заранее подготовленного клиента с историей.
3. Показать сегмент и историю покупок.
4. Показать три рекомендации.
5. Открыть подробности одной рекомендации.

Текст:

> Для клиента с историей движок строит кандидатов по графу совместных покупок. Уже приобретённые товарные группы исключаются. Для каждой товарной группы в выдаче остаётся не более одного доступного предложения каталога.

### 1:05–1:35 — Объяснимость

Показать для одной рекомендации:

- название;
- `product_id`;
- тип рекомендации;
- score;
- reason code;
- evidence;
- explanation.

Текст:

> Каждая рекомендация сопровождается объяснением и evidence. Например, можно увидеть, с каким товаром из истории кандидат встречался в одной корзине и сколько таких корзин было в обучающем периоде. Это проверяемые факты, а не свободно сгенерированные утверждения. Совместная покупка не означает доказанную техническую совместимость.

### 1:35–1:55 — B2C

1. Переключиться на B2C.
2. Выбрать клиента с историей.
3. Показать рекомендации.

Текст:

> B2B и B2C обрабатываются раздельно. Для B2C используются история покупок и сегментная логика. Отрасль и корпоративный профиль клиента в B2C-рекомендациях не используются.

### 1:55–2:20 — Cold-start

1. Выбрать клиента без истории.
2. Показать отсутствие истории.
3. Показать popularity-рекомендации.

Текст:

> Если истории покупок нет, персонализировать рекомендации по ней невозможно. В этом случае система использует популярность товаров в соответствующем сегменте. Результат явно маркируется как неперсонализированный.

### 2:20–2:45 — Архитектура и качество

Показать краткую схему или диагностические показатели.

Текст:

> В основе решения — детерминированный алгоритм: граф совместных покупок, бизнес-фильтры и popularity fallback. В диагностическом прогоне обработано 19 008 клиентов, Fill Rate составил 100 процентов для ALL, B2B и B2C. Это означает, что удалось заполнить три рекомендательные позиции, но не означает стопроцентную точность рекомендаций.

### 2:45–3:00 — Завершение

Текст:

> В результате получен работающий MVP Cross-sell Recommendation Agent с разделением B2B и B2C, обработкой cold-start и объяснениями на основе реальных данных. Приложение развёрнуто в Google Cloud Run и доступно по публичной ссылке. Базовая логика работает без LLM и внешних модельных API.

### Каталог

- 817 уникальных sales `item_id` в последнем отчёте.
- 438 `item_id` сопоставлены с предложениями каталога.

### Граф

- 813 узлов.
- 1 986 рёбер.
- Граф построен по Train до `2026-08-31`.
- Узлы графа — `item_id`.
- Граф отражает совместные покупки, а не техническую совместимость.

### Диагностика движка

- 19 008 клиентов обработано.
- 17 457 с историей; 1 551 без истории.
- Fill Rate 100% в ALL/B2B/B2C.
- 57 024 рекомендательные позиции:
  - 40 468 co-purchase;
  - 11 903 popularity fallback;
  - 4 653 cold-start popularity.
- Для клиентов с историей co-purchase составляет 77.3%, popularity fallback — 22.7% позиций. Это доли позиций, не клиентов и не Precision@3.

### Backtest baseline

- Cohort A: 337 клиентов (302 B2B, 35 B2C).
- Cohort B: 172 клиента (147 B2B, 25 B2C).
- Cohort sizes совпали с организаторами.
- Popularity совпадает с официальными результатами в пределах округления.
- Co-purchase имеет расхождения с официальными результатами; причина требует отдельного анализа.

## 5. Формулировки, которых следует избегать

Не говорить:

- «Система увеличивает продажи/конверсию».
- «Рекомендуемые товары технически совместимы».
- «Каталог полностью покрывает все товары».
- «Fill Rate 100% означает 100% точность».
- «LLM подбирает товары».
- «Система обучает модель на каждом запросе».
- «Интеграция с реальным личным кабинетом Softline уже выполнена».
- «Мобильная версия полностью проверена», пока не проведён повторный smoke test.

Не показывать цену: соответствующего поля в модели `ProductOffer` нет.

## 6. Финальная формулировка

> В результате получен работающий MVP Cross-sell Recommendation Agent: он разделяет B2B и B2C, учитывает историю покупок, фильтрует уже приобретённые товарные группы и недоступные предложения, возвращает Top-3 и объясняет рекомендации через проверяемые факты. Cold-start обрабатывается popularity fallback. Приложение упаковано в Docker и развёрнуто в Google Cloud Run. Базовый алгоритм не зависит от LLM и внешних модельных API.
