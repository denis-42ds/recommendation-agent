# DEMO SCRIPT — Recommendation Agent

**Дата:** 27.11.2026
**Назначение:** короткая запись локального MVP для хакатона.

## 1. Что демонстрируем

Локальный Recommendation Agent для личного кабинета Softline:
- выбор B2B/B2C клиента;
- персональные Cross-sell рекомендации по истории;
- evidence и объяснение каждой рекомендации;
- cold-start через popularity fallback;
- Fill Rate и ограничения каталога.

**Не заявляем:** рост конверсии/выручки, техническую совместимость товаров, готовность публичного Cloud Run деплоя без отдельной проверки.

## 2. Подготовка перед записью

1. Активировать виртуальное окружение.
2. Проверить наличие локальных файлов датасета и артефактов.
3. Выполнить:
   ```bash
   ruff check
   python -m pytest -q
   ```
4. Запустить:
   ```bash
   streamlit run app.py
   ```
5. Открыть локальный URL Streamlit.
6. Для записи использовать только разрешённые данные. Если запись будет опубликована, убедиться, что клиентские идентификаторы и сведения обезличены или заменены синтетическими.

## 3. Сценарий записи

### Кадр 1 — постановка задачи

Текст:
> Это MVP рекомендательного агента для личного кабинета интернет-магазина Softline. В рамках хакатона сфокусировались на Cross-sell: система предлагает товары на основе истории совместных покупок и дополняет выдачу популярными товарами сегмента, если персональных кандидатов недостаточно.

Показать заголовок приложения и интерфейс выбора сегмента/клиента.

### Кадр 2 — клиент с историей

1. Выбрать B2B или B2C.
2. Выбрать клиента с историей.
3. Показать сегмент и историю покупок.
4. Запустить/показать рекомендации.

Текст:
> Для клиента с историей движок строит кандидатов по графу совместных покупок. Уже приобретённые товарные группы исключаются. В выдаче остаётся не более одного предложения на товарную группу.

### Кадр 3 — объяснимость

Для одной-двух рекомендаций показать:
- название и `product_id`;
- тип рекомендации;
- score;
- reason code;
- evidence;
- explanation.

Текст:
> Объяснение не генерирует новые факты. Оно формируется детерминированно из evidence: например, показывает, с каким товаром из истории кандидат встречался в одной корзине и сколько таких корзин было в Train. Совместная покупка не трактуется как доказательство технической совместимости.

### Кадр 4 — fallback

Если интерфейс позволяет, выбрать клиента, у которого co-purchase кандидатов недостаточно для трёх позиций.

Текст:
> Если персональных кандидатов недостаточно, оставшиеся позиции заполняются популярными товарами соответствующего сегмента. Источник рекомендации отражается в reason code.

Не обещать конкретный fallback-сценарий для выбранного клиента, пока его фактический результат не проверен на экране.

### Кадр 5 — cold-start

1. Выбрать клиента без истории.
2. Показать, что история отсутствует.
3. Показать popularity рекомендации.

Текст:
> Для cold-start персонализация по истории невозможна, поэтому используется popularity соответствующего сегмента. Такой результат явно маркируется как неперсонализированный.

### Кадр 6 — качество и ограничения

Показать краткую сводку:
- 19 008 клиентов обработано в диагностическом прогоне;
- Fill Rate 100% для ALL, B2B и B2C;
- Top-3 был заполнен всем клиентам в этом прогоне;
- 17 457 клиентов имели историю, 1 551 — не имели.

Текст:
> Fill Rate показывает, насколько часто система может заполнить три слота допустимыми товарами. Это не метрика релевантности и не доказательство роста продаж. Для качества рекомендаций отдельно используется offline backtest с Precision@3.

## 4. Проверенные факты для озвучивания

### Каталог
- 817 уникальных sales item_id в последнем отчёте.
- 438 item_id сопоставлены с предложениями каталога.
- 379 item_id не сопоставлены.
- `matched_products.json`: 552 записи предложений.
- Движок использует только доступные сопоставленные предложения.

### Граф
- 813 узлов.
- 1 986 рёбер.
- Граф построен по Train до `2026-08-31`.
- Узлы графа — `item_id`.
- Граф отражает совместные покупки, а не техническую совместимость.

### Диагностика движка
- 19 008 клиентов обработано.
- 17 457 с историей; 1 551 без истории.
- Fill Rate 100% в ALL/B2B/B2C.
- 57 024 рекомендательные позиции:
  - 40 468 co-purchase;
  - 11 903 popularity fallback;
  - 4 653 cold-start popularity.
- Для клиентов с историей co-purchase составляет 77.3%, popularity fallback — 22.7% позиций. Это доли позиций, не клиентов и не Precision@3.

### Backtest baseline
- Cohort A: 337 клиентов (302 B2B, 35 B2C).
- Cohort B: 172 клиента (147 B2B, 25 B2C).
- Cohort sizes совпали с организаторами.
- Popularity совпадает с официальными результатами в пределах округления.
- Co-purchase имеет расхождения с официальными результатами; причина требует отдельного анализа.

## 5. Формулировки, которых следует избегать

Не говорить:
- «Система увеличивает продажи/конверсию».
- «Рекомендуемые товары технически совместимы».
- «Каталог полностью покрывает все товары».
- «Fill Rate 100% означает 100% точность».
- «Cloud Run уже опубликован», пока нет проверенного URL и smoke test.
- «LLM подбирает товары» — базовый движок работает без LLM.

## 6. Финальная формулировка

> В результате получен локально работающий MVP Cross-sell Recommendation Agent: он разделяет B2B и B2C, учитывает историю покупок, фильтрует уже приобретённые товарные группы и недоступные предложения, возвращает Top-3 и объясняет рекомендации через проверяемые факты. Cold-start обрабатывается popularity fallback. Следующий этап — подтверждение Docker/Cloud Run деплоя и дальнейшая диагностика расхождений Co-purchase в backtest.
